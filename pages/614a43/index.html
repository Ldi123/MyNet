一个普通话学习站的完整复盘

# 从 0 到 1：一个普通话学习站的完整复盘

这是一个"跑通了，但已经死了"的项目。 它的技术全部可用、部署全部成功，唯一的问题是——没人再需要它了。 正因如此，它比那些只写成功经验的复盘更有记录价值。

# 写在最前

2026 年 8 月底，我用两个晚上做了一个普通话二级考试辅助学习站：Flask 后端 + 原生前端 + Docker Compose 部署，包含听音选拼音、三关闯关、错题本、数据看板、录音 A/B 对比。它真的上线了，也真的被用过。

这不是一篇纯手写的项目——全程是和 AI 结对完成的。从目录结构、题库数据、Flask 接口到 nginx 配置，绝大部分代码由 AI 生成，我负责提需求、做判断、验证结果，以及踩坑之后的归因。

所以这不是一篇单纯的踩坑记录。我会尽量说清楚：AI 在哪里真的提了效，在哪里反而成了风险源。

然后需求消失了。考试结束，没有人再打开它。

若干天后我回来做处置评估，逐行读了代码，结论是：这个项目没有留下任何值得带走的代码。四个看起来"可复用"的模块，拆开看要么是直接调现成包再套一层胶水，要么是浏览器标准 API 的常规封装，要么干脆是已被判定有缺陷的实现。

它真正留下的只有三样东西：一条被验证过的选型结论、一条产品教训、以及这篇文章。

下面是我认为值得记下来的部分。

# 一、项目与时间线

时间 进展
D1 晚 从零搭建：Flask + pypinyin 后端，原生前端三模块（拼音卡片 / 计时器 / 录音波形）
D1 晚 需求迭代，推翻重做为"闯关刷题"：听音选拼音 · 三关 · 错题本 · 录音对比
D1 晚 Docker Compose 双容器部署上线，配置 HTTPS
D2 上午 修两个线上问题：随机选词按钮遮挡卡片、标准音没声音（改用后端 TTS）

从空目录到线上可用，用了两个晚上。 支撑这个速度的一是选型、二是全程有 AI 结对，后面的章节会分别展开。

前端  原生 HTML/CSS/JS，无框架、无构建、无 CDN
后端  Flask + pypinyin + edge-tts，gunicorn 单 worker

# 二、架构选型：为什么刻意选择"无框架"

这不是偷懒，是算过账的。

对一个生命周期可能只有几周、功能边界清晰、单人开发的小项目，引入前端框架意味着：构建链路、依赖安装、热更新配置、产物体积、以及"改一行要等几秒"的心智负担。而原生三件套的代价只是多写一点 DOM 操作。

但真正让天平倾斜的，是这次有 AI 结对。

"原生 JS 太啰嗦"这个反对理由，本质上是手写成本的问题。而当代码主要由 AI 生成时，这个成本几乎归零——多写几十行 DOM 操作，我并不需要多付出任何时间。于是选型公式变了：

判断式 结论
无 AI 结对 无框架的收益 < 手写样板的成本 上框架
有 AI 结对 无框架的收益 > 趋近于零的生成成本 不上框架

AI 没有让框架变得更好用，它让"不用框架"这个选项变得可行。 这是这次我对 AI 提效最具体的一次体感——不是"写代码变快了多少"，而是它改变了技术选型的成本结构，让某个原本不划算的选项变成了最优解。这类收益比单纯的代码生成速度要值钱得多，也更难被注意到。

真正让这个决策落地的，还有部署侧的配合：

volumes:
  - ./frontend:/usr/share/nginx/html:ro
1
2

前端目录直接挂载进容器，改完 JS 刷新即可，不需要 build、不需要重建镜像。这让"改一行→看效果"的循环压到 1 秒以内。开发反馈速度才是小项目最大的生产力，而框架在这件事上是减分的。

后端则相反——改后端要 docker compose build backend && up -d，一次几十秒。这个不对称后来影响了我的开发习惯：能放前端的逻辑尽量不写进后端。

可迁移的结论：单人、短周期、功能边界清晰的项目，"无构建"方案的整体效率高于任何框架。判断标准是——你的项目有没有"多人协作 + 长期演进 + 复杂状态"这三个需求中的任意一个。一个都没有，就别上框架。

# 三、七个坑

# 坑 1｜把浏览器 API 当基础设施，是这次最大的判断失误

现象：点"播放标准音"毫无反应。

根因：标准音最初完全依赖浏览器的 speechSynthesis。这个 API 在服务器部署环境下极不可靠——

  1. 无头/服务器环境可能根本没有中文语音包，getVoices() 返回空数组；
  2. Chrome 对它有限制严格的自动播放策略，还有个著名的"首次调用 15 秒无声"bug；
  3. 非 HTTPS、非 localhost 时部分能力被直接限制。

解决：后端用 edge-tts 合成 mp3，前端改成播音频文件，浏览器 API 降级为兜底。

# 同步封装异步库，配合线程锁避免阻塞 Flask 主线程
def _tts_sync(text, voice):
    import edge_tts
    async def _gen():
        communicate = edge_tts.Communicate(text, voice)
        buf = bytearray()
        async for chunk in communicate.stream():
            if chunk["type"] == "audio":
                buf.extend(chunk["data"])
        return bytes(buf)
    return asyncio.run(_gen())

audio.onerror = () => speakFallback(text);   // mp3 失败 → 回退 Web Speech API

教训：凡是涉及语音、录音、摄像头的浏览器能力，默认假设它在目标环境不可用。主方案要走后端出文件，前端 API 只能当 fallback，不能当依赖。

顺带一条硬信息：edge-tts 是微软的免费 TTS，不需要 API key，直接输出 mp3，连 ffmpeg 都不需要，中文语音质量相当好。以后做任何需要中文朗读的东西，这条能省一小时探索。

# 坑 2｜依赖版本号是最容易"看起来确定"的幻觉

现象：docker compose build 直接失败：No matching distribution found for edge-tts==7.1.9。

根因：我凭印象写了版本号 7.1.9，这个版本根本不存在。可用版本从 7.1.0 直接跳到 7.2.0，而新版要求 Python ≥ 3.10，容器里是 3.9。

教训：版本号是那种"写出来特别像真的、错起来毫无征兆"的信息。锁定依赖前必须验证两件事——版本号真实存在，且兼容运行环境的 Python 版本。报错日志里 from versions: ... 列出的就是可用版本，直接照抄。

顺便交代一句：这个 7.1.9 就是 AI 给的。

说这个不是为了吐槽——恰恰相反，它精准标出了 AI 辅助开发里最需要人把关的那一类信息：版本号、API 签名、配置项名称、端口号。这些"看起来极其确定、错起来毫无征兆"的事实性细节，是模型的幻觉高发区。

我的分工后来固定成这样：代码可以放手让 AI 生成，但凡是写进 requirements.txt、配置文件和部署脚本里的"事实"，一律以实际执行结果为准。 生成阶段可以快，验证环节不能省。

# 坑 3｜精简镜像里什么都没有

现象：docker exec pth2-backend curl ... 报 executable file not found。

根因：python:3.9-slim 和 nginx:alpine 都是精简镜像，没有 curl，alpine 甚至没有 bash。

解决：

  • 后端容器内测：用 python3 -c "import urllib.request; ..."
  • 宿主机验证：走 nginx 反代 curl -sk https://localhost/api/...
  • nginx 容器：用 busybox 自带的 wget

教训：进任何精简镜像，先 which curl bash 探底，别默认什么都有。

# 坑 4｜HTTPS 一旦开了，本地验证习惯要整个换掉

现象：curl http://localhost/api/health 返回 301，看不到 JSON。

根因：nginx 配了 80 → 443 强制跳转，普通 http 请求全被重定向。又因为证书是自签的，不加 -k 会 SSL 验证失败。

解决：所有本地验证统一改成 curl -sk https://localhost/api/...。

教训：启用 HTTPS 的那一刻起，所有调试命令要一次性全部切换，否则会浪费大量时间在"为什么拿不到内容"上。

# 坑 5｜绝对定位：负 margin 往里叠，负 top 往外放

现象：录音视图的"随机选词"按钮压在卡片文字上。

根因：

/* 错误：负 margin 把按钮往内容里拽 */
position: absolute; right: 16px; margin-top: -44px;
1
2

解决：

/* 正确：负 top 放到卡片边界之外 */
position: absolute; top: -40px; right: 0;
1
2

教训：想让元素出现在容器"外侧"，用负值的 top / bottom 推出边界；用负 margin 只会把它叠进内容里。动手前先确认父容器是谁（这里需要 .record-pick { position: relative }）。

# 坑 6｜改了代码没生效？先看版本号

静态资源加版本号参数：

<script src="script.js?v=20260829d"></script>
1

改完代码忘记递增，用户看到的就是旧文件。这是最容易被误判为"代码写错了"的问题。

# 坑 7｜512MB 内存下的 gunicorn

服务器是 4 核 4G，后端容器限 512MB。多 worker 会超，所以：

gunicorn --workers 1 --threads 4
1

Flask 同步请求 + 单 worker 多线程足够。edge-tts 是异步库，在视图函数里用线程锁 + asyncio.run() 同步封装，单 worker 下多线程各自 asyncio.run 是安全的。

# 四、真正的教训：技术跑通 ≠ 教学有效

前面七个坑都是工程问题，修完就完了。但复盘时我发现了一个更根本的、当时完全没意识到的问题——它不在工程层面，在产品层面。

干扰项是这样生成的：

def generate_distractors(correct_pinyin, pool, count=3):
    candidates = []
    for item in pool:
        if item["pinyin"] == correct_pinyin:
            continue
        cand = item["pinyin"]
        if cand not in candidates:
            candidates.append(cand)
    random.shuffle(candidates)
    return candidates[:count]

逻辑没问题，测试能过，界面显示正常。但实际效果是什么？

正确答案是 nài（奈），干扰项可能是 yuè（粤）、quàn（券）、sài（赛）。

这种选项一眼就能排除，训练价值为零。

普通话学习真正有效的干扰项是最小对立对：nài / lài（n/l 不分）、zī / zhī（平翘舌）、mín / míng（前后鼻音）。只有让学习者在最容易混淆的两个音之间做选择，训练才成立。

问题出在哪？出在数据结构，不出在算法。

题库里每条记录长这样：

{"id": "l1_001", "word": "奈", "pinyin": "nài", "type": "shengmu", "note": "n 与 l 区分"}
1

note 里写着"n 与 l 区分"，说明我在录入数据时是知道混淆关系的——但这个知识只写进了给人看的注释，没有变成机器可用的字段。正确做法是每题显式带一个 confusable 字段：

{"word": "奈", "pinyin": "nài", "confusable": ["lài", "nà", "nǎi"]}
1

干扰项靠数据定义，不靠算法随机。随机算法再精巧，也造不出 pedagogically 有效的选项。

可迁移的结论：当一个功能"技术上跑通了但效果不好"时，先别优化算法，去检查数据结构——很可能是你在数据录入时丢掉了关键信息。算法只能利用已有的信息，无法凭空补上。

这里还有一层，是 AI 时代尤其要警惕的：这段干扰项代码是 AI 写的，它写得完全正确，测试全绿，但它不知道这题的教学目的是什么。

AI 能高效地产出"技术上跑通"的实现，而"这个实现到底有没有达成它存在的目的"——这是需求方的责任，无法外包，也不会有人替你报错。功能有效性是 AI 辅助开发中最容易失守的一环，因为它失败得悄无声息。

同一类问题还有一处：掌握度算法。

return Math.min(1, p.correct / total);   // 分子累计答对次数，分母关卡题目总数
1

分子是累计答对次数，分母是关卡题目总数。反复刷同一批简单题就能把掌握度顶满并解锁下一关——学习机制形同虚设，可被轻易刷分。

（对比一下：我另一个项目用的是 FSRS 间隔重复算法，在这个维度上明显更靠谱。讽刺的是，我当初还打算把这个"答题引擎"抽出来复用——一个已知有缺陷的实现，抽它干什么。）

# 五、复盘：做对了什么，做错了什么

做对的：

  1. 选型克制。无框架、无构建、无 CDN，把复杂度压到最低，这是能在两个晚上内交付的直接原因。
  2. 部署方式选对了。前端 volume 热更新让迭代循环压到 1 秒；后端不映射宿主机端口，只走 nginx 反代，既安全又省了跨域配置。
  3. 关键能力做了降级兜底。TTS 主方案失败回退浏览器 API，这个设计让"标准音没声音"没有变成致命故障。
  4. 边做边记坑。PROJECT_NOTES.md 是这次唯一真正沉淀下来的东西——如果不写，一周后这些细节全部蒸发。
  5. 把 AI 放在了正确的位置。让它产出大量确定性代码（题库数据、CRUD 接口、CSS 布局、nginx 配置），我集中精力做需求判断、线上归因和有效性验证。前提是把好"事实性信息"这一关（坑 2）。

做错的：

  1. 没建 git 仓库。一个已经上线的项目，居然没有任何版本历史。这是本次最高优先级的风险，也是最不应该犯的错。
  2. 把浏览器 API 当基础设施（坑 1）——对运行环境做最坏假设，应该成为默认习惯。
  3. 只验证"功能可用"，没验证"效果有效"。干扰项那个问题，测试全绿、界面正常，但产品是失败的。功能测试覆盖不了有效性。
  4. 数据与代码耦合。153 条题库硬编码在 app.py 里，换主题就得改源码。
  5. 没有及时止损的判断框架。项目该不该继续，我是在一个月后才回头评估的——如果一开始就想清楚"这是为一场考试做的临时工具"，很多设计会更果断。

# 六、如果重来一次

  1. 第一天就 git init。没有例外。
  2. 题库外置。数据放 JSON/SQLite，代码只负责逻辑——这样换主题时不用碰代码，也才谈得上"复用"。
  3. 先设计数据结构再写算法。干扰项、掌握度这两个问题的根源都在这里。数据结构对了，算法可以很笨。
  4. 给项目预设一个退出条件。"为 X 考试做的工具，考完即归档"——写清楚，到时候就不用纠结。
  5. 录音功能重新评估必要性。受"不使用语音识别模型"的约束，录音只能做人耳 A/B 对比，没有客观反馈，实际使用率很低。约束导致功能价值存疑时，应该早点砍掉，而不是做出来凑数。

# 七、一页速查

事项 结论
小项目选型 单人、短周期、无复杂状态 → 无框架无构建，整体效率更高
语音/录音/摄像头 后端出文件为主，浏览器 API 只做 fallback
免费中文 TTS edge-tts：无需 key、输出 mp3、不需要 ffmpeg
锁依赖版本 先验证版本号存在 + 兼容运行环境的 Python 版本
精简镜像 slim/alpine 没 curl 没 bash，先 which 探底
启用 HTTPS 后 本地验证一律 curl -sk https://...
前端改代码 volume 挂载刷新即生效，但要递增 ?v= 版本号
绝对定位放外侧 用负 top/bottom，不要用负 margin
小内存部署 gunicorn 单 worker 多线程 + mem_limit
效果不好时 先查数据结构，别急着优化算法
第一天 git init

# 最后

这个项目的结局是归档，我不觉得可惜。

它在很短的时间里完整地走了一遍"需求 → 设计 → 实现 → 部署 → 线上修复 → 复盘"的全过程，代价极低。真正昂贵的做法是：因为"已经写了这么多代码"而舍不得停，或者因为"想保留资产"而去做没有目标的通用化重构。

最后说说 AI。它在这个项目里确实大幅提效了，但提效的方式和通常的说法不太一样——不是"少写了多少行代码"：

  • 它改变了技术选型的成本结构，把"不用框架"从将就变成了最优解；
  • 它把样板代码的成本压到接近零，让我能把注意力全部放在需求判断和线上归因上；
  • 但它不会替你判断功能是否有效，也不会为那个幻觉出来的版本号负责。

前两条是增量，第三条是代价。而第三条恰恰是最容易被忽略的，因为它不像 build 失败那样会报错。

代码是最不值钱的那部分。判断力才是——而在 AI 时代，这句话比以往任何时候都更成立。
